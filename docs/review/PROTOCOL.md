# Протокол кросс-ревью

Две нейросети проверяют работу друг друга. Напрямую они не общаются: канал - **один markdown-файл на ревью**
в `docs/review/threads/`. Каждая сторона дописывает в конец свой ход и передает очередь. Человек - арбитр.

## Роли
- **Автор** - сделал изменения (ветка, коммиты), отвечает на замечания и исправляет.
- **Ревьюер** - проверяет, пишет замечания, проверяет исправления. Код автора сам не правит и в его ветку не коммитит.
- **Человек** - передает очередь между сторонами, решает споры, закрывает ревью.

## Файл ревью
`docs/review/threads/ГГГГ-ММ-ДД-<тема>.md`, по шаблону [TEMPLATE.md](TEMPLATE.md). Сверху - шапка, ниже - ходы, только дописываются
(старые ходы не правим и не удаляем).

```
status: open | changes-requested | approved | escalated | closed
turn: reviewer | author | human
round: 1
```
`turn` - чей сейчас ход. Закончил ход - обновил `status`, `turn`, `round` и сказал человеку одну строку: «ход: <кто>, файл <путь>».

## Ходы
Каждый ход - раздел `## <номер>. <ТИП> - <роль> (<модель>), <дата>`.

1. **REQUEST** (автор): что проверить - ветка, коммиты (`base..head`), цель, на что смотреть особо, как проверить
   (команды тестов), ссылки на `docs/kb`. `turn: reviewer`.
2. **REVIEW** (ревьюер): замечания в формате ниже + что проверил сам. Есть blocker/major - `changes-requested`, иначе `approved`.
   `turn: author` (или `human`, если `approved`).
3. **REPLY** (автор): ответ на **каждое** замечание по id. `round` +1, `turn: reviewer`.
4. **VERIFY** (ревьюер): по каждому ответу - принято или нет. Все закрыто - `approved`, `turn: human`.
5. **CLOSE** (человек): итог, `status: closed`.

Не больше **3 раундов** REPLY/VERIFY. Не сошлись - `status: escalated`, `turn: human`, коротко: в чем спор и позиции сторон.

## Замечание
```
### F1 [blocker] server/src/payments/payments.service.ts:142 - уведомление обрабатывается дважды
Что не так: <одно-два предложения>
Доказательство: <как воспроизвести / какой тест падает / цитата кода>
Предлагаю: <как исправить>
Уверенность: подтверждено | вероятно
```
- Важность: **blocker** (ломает критерии приемки, данные, безопасность, деньги), **major** (баг в реальном сценарии),
  **minor** (неудобство, слабое место), **nit** (стиль - не больше 3 на ревью, не повод для `changes-requested`).
- Id - `F1, F2...` сквозные по ревью; новые замечания в VERIFY - со следующими номерами.
- Только проверяемое: путь и строка, доказательство. «Подтверждено» - только если сам воспроизвел или прогнал тест.

## Ответ автора
```
F1: исправлено в <sha> - <что сделано, какой тест добавлен>
F2: не исправляю - <почему>
F3: не согласен - <аргумент и доказательство>
F4: вопрос - <что непонятно>
```

## Правила
- Проверять **только заявленный диапазон** коммитов; соседние проблемы - отдельным замечанием `minor` с пометкой «вне диапазона».
- Сверяться с `docs/kb` (решения в `decisions.md` не оспаривать без нового довода) и с критериями приемки (план недели).
- Тесты и сборку прогонять самому; не выдумывать результаты - «не запускал» так и писать.
- Верстку - только против макета (самые новые фреймы, `docs/kb/workflow.md`); вкусовщина - не замечание.
- В файл ревью не писать секреты, токены, ссылки на материалы заказчика (репозиторий публичный).
- Файл ревью коммитится вместе с исправлениями (так он переезжает между компьютерами); после `closed` - больше не меняется.
- Итоговые выводы (новое решение, грабли) - автор переносит в `docs/kb` в последнем коммите ревью.

## Команда «РЕВЬЮ»
Человек пишет агенту одно слово **РЕВЬЮ** (регистр не важен) - агент продолжает процесс сам. Кто он, агент знает из
своего файла инструкций: Codex - `AGENTS.md`, Claude - `CLAUDE.md`. Роль в конкретном ревью - по шапке файла
(`автор:` / `ревьюер:` содержит его имя).

**`РЕВЬЮ`** - продолжить:
1. Прочитать этот протокол и все файлы в `docs/review/threads/` со `status`, отличным от `closed`.
2. Есть ревью, где `turn` - твоя роль: сделать этот ход строго по протоколу (если таких несколько - по очереди, от старых к новым),
   обновить шапку и в конце ответить одной строкой на каждое: «<файл>: сделан <ТИП>, ход: <кто>».
3. Твоего хода нет нигде - **ничего не менять** и предупредить: «Сейчас не мой ход: <файл> - ход <кто> (status <...>)»
   по каждому открытому ревью. Если `turn: human` - подсказать человеку, что от него ждут
   (`approved` - закрыть: написать «РЕВЬЮ закрой» автору; `escalated` - решить спор и сказать, кто прав).
4. Открытых ревью нет - так и сказать.

**`РЕВЬЮ <тема>`** - начать новое ревью, ты автор: создать файл по шаблону, собрать диапазон коммитов по теме
(спросить человека, если неясно), написать REQUEST, `turn: reviewer`, ревьюер - вторая нейросеть.

**`РЕВЬЮ закрой`** - только автору и только при `status: approved`: дописать CLOSE от имени человека («закрыто по команде
человека»), перенести выводы в `docs/kb`, `status: closed`, `turn: human`.

Работа в одной папке: ревьюер свой ход не коммитит - его правку файла ревью коммитит автор вместе со своим следующим ходом
(или с исправлениями). Автор перед ходом смотрит `git status`, чтобы не затереть несохраненный ход ревьюера.

## Как подключить вторую нейросеть
Обычно не нужно: Codex сам читает `AGENTS.md`, Claude - `CLAUDE.md`, достаточно написать **РЕВЬЮ**.
Если инструмент не читает эти файлы - дать ему в начале сессии (подставив путь к файлу ревью):

> Ты участвуешь в кросс-ревью проекта EzMarket. Прочитай `docs/review/PROTOCOL.md`, `docs/kb/INDEX.md` и файл ревью
> `docs/review/threads/<файл>.md`. Посмотри поля `status` и `turn`: если сейчас твой ход - сделай его строго по протоколу
> (формат замечаний и ответов, обнови шапку), если нет - ничего не меняй и скажи, чей ход. Свою роль (автор или ревьюер)
> возьми из шапки файла.
