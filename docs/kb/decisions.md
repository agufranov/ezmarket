# Решения

Короткий журнал: что решили, почему, что отвергли. Новое - сверху.

### Уведомления - триггерами по строкам истории, текст - в API (2026-10-27)
«На каждую смену статуса» гарантирует база: строку истории статусов пишет триггер при любом переходе, уведомление
создается от нее в той же транзакции, уникальный `history_id` - ровно одно. Так же с бонусами (`bonus_tx_id`).
Отвергли создание в коде сервисов: переходов несколько путей (сервис, воркер, платежка) - легко пропустить один.
В строке уведомления только ссылка на источник, текст собирает API - тексты правятся без миграций.
Письмо - только об итоге оплаченного заказа и через очередь `email_outbox` в транзакции перехода: сбой почты не
откатывает заказ, письмо не теряется и не дублируется.

### Бонусы: баланс + журнал, списание условным UPDATE, возврат и кэшбэк - триггером (2026-10-27)
Тот же прием, что со статусом заказа. Баланс - колонка: условный `UPDATE ... WHERE bonus_balance >= N` держит «не ниже 0»
и «из 20 одновременных проходит 1» без блокировок в коде; каждое изменение - строка журнала с остатком (история).
Возврат и кэшбэк - триггер на смену статуса: срабатывает при любом пути перехода в той же транзакции, уникальный индекс
`(order_id, kind)` делает начисление однократным. Кэшбэк считается при создании заказа и хранится в нем - смена процента
не меняет уже созданные заказы. Отвергли: баланс как сумма журнала на каждый запрос (на каждое списание нужна блокировка
пользователя) и начисление в коде сервисов (легко пропустить один из путей перехода).
Правила - из макета и FAQ (до 30% заказа, кэшбэк до 5%, 1 бонус = 1 ₽ - поэтому только рубли), +100 за регистрацию - ТЗ 12.8.

### Почта стенда - Resend по SMTP со своего домена (2026-10-27)
Сначала без домена: Resend слал с `onboarding@resend.dev`, но только на почту владельца аккаунта. Gmail, Яндекс и Mail.ru
по SMTP со стенда не подходят - у них только 465/587, а VPS их режет; Brevo с подтвержденным Gmail-адресом - без домена,
но письма от @gmail.com через чужой сервер уходят в спам. Поэтому купили домен (регистратор и имя - `access.local.md`),
подтвердили его в Resend, `MAIL_FROM` - `no-reply@` этого домена, на стенде `AUTH_DEMO_CODE=false`: код только в письме.
Тот же домен ведет на сайт стенда (A-записи на IP) - nginx без `server_name`, на сервере менять ничего не пришлось.
Код не менялся - только `.env` стенда (`MAIL_FROM`, `SITE_URL`, `AUTH_DEMO_CODE`).

### Переход статуса - только из прочитанного состояния; выполнение - с захватом на срок (2026-10-26, кросс-ревью Codex)
Ревью нашло гонки там, где код читал заказ, а переводил его «из любого неоплаченного»: отмена и истечение проходили
мимо только что созданного счета Crypto Pay, `/pay` истекал оплаченный счет. Правило: `from` в `move` - ровно прочитанный
статус, при неудаче - перечитать и решить заново; истечение - один путь для всех точек входа.
Выполнение заказа: захват без срока навсегда терял заказ при падении процесса - теперь захват на 5 минут с перезахватом,
поставщик обязан принимать id заказа ключом повтора; `failed` - только при подтвержденном отказе.

### Лимиты суммы - с сервера, минимум - настройкой (2026-10-26)
`GET /api/orders/limits`, `ORDER_MIN_AMOUNT`. ТЗ 8.3 прямо говорит «лимиты - с бэкенда». Переменная в фронте
(`NEXT_PUBLIC_*`) зашивается при сборке Docker-образа - менять минимум на стенде пришлось бы пересборкой.

### Crypto Pay: опрос + вебхук, счет закрывается перед истечением и отменой (2026-10-26)
Вебхуки только на HTTPS, а у стенда и локалки его нет - опрос работает везде, вебхук страхует при HTTPS.
Без проверки счета перед `expired`/`canceled` оплата в последние секунды или по старой ссылке пропадала бы (`late`, ручной возврат).

### Платежка за общим событием (2026-10-26)
Тестовая платежка и Crypto Pay переводят свои уведомления в одно событие и одну функцию `applyEvent` - вся логика
«одно зачисление, сверка суммы, только из pending» в одном месте и одинаково тестируется.

### Статус в заказе + история триггером (2026-10-26)
Вопрос пользователя: «не проще ли убрать статус из заказа и полагаться на таблицу статусов?» - нет.
Условный `UPDATE ... WHERE status = 'pending'` - одна строка SQL, на ней держатся «одно зачисление», «возврат один раз»,
«переходы по правилам». С одной историей нужна блокировка или версия на каждую запись, а «истекшие», «список с текущим статусом»
требуют «последней записи по каждому заказу» без индекса. Расхождение исключено триггером в той же транзакции.
Event sourcing для 8 статусов избыточен.

### Суммы - целыми в минимальных единицах, и в API тоже (2026-10-26)
Требование плана («в копейках целым числом»); в API - те же единицы, чтобы нигде не было дробей. Фронт делит/умножает на 100.

### Ключ повтора - заголовок `Idempotency-Key` от клиента (2026-10-26)
Клиент генерирует ключ на одно нажатие; уникальный индекс `(user_id, idempotency_key)` решает и повтор, и гонку.

### Фейковые внешние сервисы на старте (2026-10-26)
Настоящей платежки и поставщика Steam не было: встроенная тестовая платежка с подписью HMAC и заглушка пополнения,
чтобы весь путь заказа проверялся тестами и на демо. Потом подключили Crypto Pay тем же интерфейсом.
